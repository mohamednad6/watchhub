WatchHub

A personal movie-watchlist web app, built and shipped to the web.

Student: Mohamed Nadoui HTML · CSS · JavaScript Firebase + Firestore TMDB API GitHub Pages

1. Introduction

WatchHub is a web application that lets a person keep one organised list of the movies they want to watch, the movies they have already seen, and what they thought of them. The problem it solves is simple and familiar: film recommendations are scattered across streaming apps, notes and browser tabs, with no single place that travels with you. WatchHub gathers everything into one clean, cloud-synced list available from any device.

This report explains why the project was built, what it does, how it is put together, how it was built, the problems met along the way, and what was learned. The application is finished and live on the web.

2. Motivation and Goals

  • One unified list instead of many scattered notes.
  • Real movie data, so every entry has a title, poster and details.
  • Accounts and cloud sync, so the list follows the user everywhere.
  • A fast, good-looking interface that works on phone and laptop alike.

The wider aim was educational: to build and ship a complete, real web app rather than a classroom exercise, and to understand how the different parts of a modern web application fit together.

3. Features

4. How It Fits Together

WatchHub is a browser application with no server of its own to maintain. It is built from four pieces that each have one clear job:

PieceRole
Web App (HTML/CSS/JS)Everything the user sees and clicks, running in the browser.
Firebase AuthenticationCreates accounts and signs users in, by email or Google.
Cloud FirestoreThe cloud database that stores each user's saved movies.
TMDB APISupplies real movie search results, posters and details.

When a user searches for a movie, the app asks TMDB and shows the results. When they save one, the app writes it to Firestore under that user's account, so signing in on another device shows the same list. Authentication decides who the user is; Firestore remembers what they saved.

5. Design Choices

The interface is dark-first on purpose: a dark background lets movie posters stand out, and a single crimson accent colour keeps the look consistent. The layout is responsive, so it stays readable on a small phone screen and a large laptop screen. Changes happen without reloading the page, which makes the app feel quick and immediate.

6. How It Was Built

The code was written by hand with the help of an AI coding assistant, which acted as a pair programmer: suggesting code, explaining errors and speeding up repetitive work. The site is hosted free on GitHub Pages, which rebuilds and publishes the site automatically each time the code is updated. There is no server to rent, configure or maintain, and the app costs nothing to run.

Development moved in small, testable steps: first the pages and layout, then movie search, then the watchlist, and finally accounts and sync. Each step was checked in the browser before moving to the next.

7. Challenges and How They Were Solved

The most valuable learning came from debugging. Three real problems stood out:

ProblemCauseFix
Sign-in failed with a confusing "API key expired" messageThe app's config pointed at the wrong Firebase project, so Google rejected the key.Traced it using Google's own raw error response, then replaced the key with the correct one.
Sign-in blocked on the live siteThe deployed domain was not on Firebase's allowed list.Added the GitHub Pages domain to Firebase's authorised domains.
Old version kept appearing after an updateThe browser cached the old JavaScript file.Hard-refreshed and confirmed the new file was actually published to GitHub.
The first bug was the most instructive. The error message was misleading, and it was tempting to trust it. Instead the raw response from Google's servers was examined directly, which revealed the real cause: the key simply did not belong to this project. That habit — checking the primary source rather than the friendly message — turned out to be the key to solving all three problems.

8. What I Learned

  • Front-end fundamentals: how HTML, CSS and JavaScript work together in a real app.
  • Firebase: how authentication and a cloud database are configured and secured.
  • Working with third-party APIs, and reading the data they return.
  • Debugging methodically: reproduce, check the real error, form a theory, test it.
  • Deployment: how a site goes from code on a laptop to a live public URL.

Above all, the project showed that a small idea, built carefully and finished, becomes something real that other people can actually use.

9. Conclusion

WatchHub meets every goal set at the start: it is a single, good-looking, cloud-synced place to track films, and it is live on the web today. It is also a complete learning journey, from a blank page to a deployed application, including the unavoidable and educational struggle of making it actually work. Future improvements could include sharing lists with friends, watch reminders, and recommendations based on ratings.
